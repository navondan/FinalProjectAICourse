# M6.5 - Evaluation run harness

## What it does

`novaops/evals/harness.py` replays a whole item set through the shared agent and writes the
two files the rest of the project needs:

```powershell
.\.venv\Scripts\python -m novaops.cli run-set --set GOLDEN-DATASETS.json `
    --output runs-golden.json --trace-index trace-index-golden.json
.\.venv\Scripts\python -m novaops.cli eval --runs runs-golden.json --output eval-report-golden.json
```

- `runs.json` is the format `cli eval` already scores: keyed by `<session-id>:<n>` for session
  turns and by the bare item ID for one-shot items (`SIMPLE_001`, `M-I-01`), with `answer`,
  `status`, `tool_history`, `evidence`, `scope` and `intent`.
- `trace-index.json` maps every run key to its item, turn, caller, Langfuse session ID
  (= thread ID), request ID and **Langfuse trace ID, captured at run time**, so filling in
  `SUBMISSION.md` does not depend on the Langfuse read API (v1 `/traces` was removed).

`--only <item-id> ...` replays a subset for spot checks. The `serve` process is **not**
needed: the harness hosts the MCP tools in-process (the same FastMCP server, called through
the same `MCPToolExecutor`), so every tool call still appears as a `tool.<name>` span.

## Isolation rules (review)

Each one-shot input and each session gets its own temporary directory holding a freshly
seeded copy of the database (`schema.sql` + `seed.sql`) and an empty checkpoint file; the
MCP server for that item is bound to that database. The developer database
`data/novaops.sqlite3` is never opened, so runs cannot be contaminated by earlier manual
testing and a write in one item (a ticket, an access request, an approval) can never
suppress or duplicate a write in another. Within a session, every turn runs in order on
**one** thread (`<item-id>-<run-tag>`) against **one** database, so history and earlier
writes carry forward exactly as they would for a real user. The FAISS index and embedder
are loaded once and shared read-only. Every case pins `as_of_date` to 2026-07-01. The caller
is the item's `caller.employee_id`; its group is resolved from the database by the agent,
never taken from the file. Golden single-turn cases name only a group, so they replay as a
fixed ordinary member of it (Regular Employee → E010, HR Group → E004, IT Group → E007);
golden sessions without a `caller_id` take the employee ID from the persona text.

## One trace per turn, failures included

Each turn uses the deterministic request ID `<item-id>:<n>` (`:1` for one-shot items) and
produces one `novaops.agent` trace. `tracing.last_trace_id()` returns the trace ID even when
the turn raised, so a failed turn is recorded as `status: "failed"` with its `error` and its
trace ID; the run continues with the next turn. Nothing is silently dropped. Items without a
caller (the optional Vendor and Renewal workflows) are listed under `skipped` in the run
summary until M7/M8 add runners for them.

## Fixes found by the first run

The first live run failed every Maya policy turn: Nova Lite wrote well-formed markdown
answers with no citations, and the Maya citation validator raised, failing the whole turn.
The answer node now (1) gives the model the exact `allowed_citations` list and the citation
contract, (2) retries once with the validator's feedback, and (3) if the draft is still
uncited, returns a safe, fully cited fallback that points to the permitted sources instead of
failing. Markdown heading lines are not treated as factual sentences.

The baseline run then showed that most remaining failures were not answers at all: any tool
error (a name passed where an employee ID was expected, an unknown policy name, a wrong
argument name) or a malformed JSON plan raised and failed the whole turn. Now:

- A failed **read** tool returns `{"error": "..."}` as its result; the error is kept in
  `tool_history` and in the trace. If a turn has an error and fewer than two tool rounds, the
  model re-plans once with the error visible (to fix the arguments or answer honestly);
  otherwise it answers. Write tools stay strict and still raise.
- A malformed plan is retried once with `plan_feedback`; if it is still malformed the agent
  answers without tools. A plan that names a hidden tool, or a write without a persisted
  approval, is still a hard `PermissionError` - those are guards, not formatting mistakes.
- `get_employee` accepts an employee ID, email or exact full name. An identifier that resolves
  to nobody still gets the same generic "not permitted" refusal, so the tool cannot be used to
  discover who exists. `check_software_subscription` matches names case-insensitively, and an
  unknown `get_policy` name lists the available policy names.
- The Maya checklist and Webex diagnosis nodes resolve the target through `get_employee`
  first and use the returned employee ID for every later call, the approval record and the
  write. If the target cannot be resolved or is not visible to the caller, the turn ends
  `blocked` with a cited "no action was taken" answer and no further tool calls.
- A requested-but-hidden **read** tool is never executed; the planner is told it is not
  available and re-plans. A hidden write tool is still a hard error.
- The onboarding checklist is retried once with the validation error. Because every field is
  copied from, and validated against, database rows, a second failure builds the checklist
  directly from those rows (with row-quote citations) instead of failing the turn.

The scorer compared golden `expected_sources` / `forbidden_sources` by exact equality, but
the golden file lists path suffixes (`equipment_policy.md`, `manager_playbook/promotion.md`)
while the agent records full paths. Sources now match by path suffix, so expected sources can
pass and forbidden (leaked) sources are actually caught. Golden sources naming database tables
(`contracts`, `onboarding_tasks`) still never match a document path; they are left strict.

## Tests

`tests/test_harness.py` (fake model, no AWS): golden and evaluation plans parse to the right
callers and run keys (27 required evaluation turns; 6 optional items skipped); each item gets
a freshly seeded database while session turns share one database and thread; a failing turn is
recorded and the run continues; a real-graph session carries history and its run file is
accepted by `cli eval`.
